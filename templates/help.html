Getting Started wizard

What it's for Open →

A single guided page for first-run setup, instead of hand-editing a long list of environment variables blind: required cluster basics (fleet nodes, Pi-hole admin password, SSH trust) followed by every optional feature — VIP/failover, external DHCP source, notifications, NetBox import, admin login — each showing whether it's already configured. It doesn't do anything the individual tabs can't already do; it just puts every setting in one place with sensible current-state indicators.

Restart required, sometimes: nodes, SSH trust, DHCP failover enable, and admin login all take effect immediately (they're stored in /data, not the environment). Pi-hole admin password, SSH user, VIP, external DHCP/UniFi, the notification webhook, and NetBox credentials are still plain environment variables read once at container start — saving one of those shows a banner listing exactly which variables changed and need a container restart (Dockge: stop then start the stack) to actually take effect.

Overview

Pihole Fleet Manager is a sidecar app for a multi-node Pi-hole v6 cluster. Pi-hole itself has no concept of "the other nodes" — every Pi-hole instance is independent, so this app is what makes a group of them behave like one fleet: one place to define extra DHCP scopes, one place to keep settings in sync, one place to see what changed and when.

Everything here talks directly to each node's own IP address — seeded once from PIHOLE_IPS, managed afterward from the Fleet Nodes section — and, for anything that needs to write files, over SSH. Nothing requires a load balancer or virtual IP in front of the cluster — the one exception is the Failover tab, which is entirely optional. See that section below.

Everything is open by default (no login) and inert unless configured for anything opt-in — see Admin login, Notifications, and NetBox import if you want those.

VLANs & DHCP scopes

What it's for Open →

Pi-hole's own Settings page only lets you configure one DHCP scope. This tab lets you define any number of additional scopes ("VLANs") — each with its own subnet, gateway, IP range, lease time, and static host reservations — and pushes them out to every node as a dnsmasq.d config snippet, alongside Pi-hole's native scope.

The "Primary" VLAN at the top of the list isn't something you create — it's a read-only mirror of whatever DHCP scope is already configured natively in Pi-hole's own Settings. Its hosts are the actual reservations from Pi-hole's API, always live, not stored locally.

Adding hosts: expand a VLAN and use the form at the bottom to reserve a MAC → IP (with an optional hostname). Any device that already has an active lease in that VLAN's subnet shows up automatically, tagged DYNAMIC — click its IP or MAC to turn it into a permanent static reservation.

Conditional Forward Domain (optional, per VLAN): Pi-hole's own Settings UI only supports one conditional-forwarding domain/subnet fleet-wide. Setting this per VLAN lets devices in that VLAN resolve local domain names (e.g. reverse DNS for a router's own admin hostname) without touching Pi-hole's native single setting.

Pi-hole Group (optional, per VLAN): see Group assignment below.

Push to Pi-hole

Nothing you do on the VLANs tab takes effect on the actual Pi-hole nodes until you click Push scopes to all Pi-holes. A push does all of the following, per node, in order:

  • Validates the full VLAN set first — if any two VLANs overlap, or a host/range falls outside its own subnet, the entire push is blocked before anything is written anywhere.
  • Writes the rendered dnsmasq.d file over SSH.
  • Flips Pi-hole's misc.etc_dnsmasq_d setting on so the file actually gets read.
  • Reloads DNS (pihole restartdns) so the new scopes take effect immediately.
  • Syncs VLAN-derived hostname DNS records — see Hostname resolution.
  • Assigns each VLAN's clients to its configured Pi-hole group, if one is set — see Group assignment.

Use Preview generated config to see exactly what will be written, without pushing anything. If a node already has scopes from a different/older instance pointed at the same cluster, the Import flow (on the same page) can pull those back into the local store instead of you re-entering them by hand.

Per-VLAN group assignment

Pi-hole supports assigning different blocklist policies ("groups") to different clients — but only per individual client (by MAC/IP), never per subnet/VLAN. Setting a Pi-hole Group name on a VLAN (on the VLANs tab) closes that gap: every push assigns every client currently in that VLAN — static reservations and active dynamic leases alike — to the named group, via Pi-hole's /api/clients.

The group itself has to already exist on a node for this to take effect there — if it doesn't yet, the push logs a warning for that node (rather than failing the whole push) telling you the group name wasn't found. Create the group once on any node's own Pi-hole UI (Group Management), or let replication's group reconciliation propagate it to the rest of the fleet automatically.

Fleet-wide hostname resolution

Each of the 3 Pi-hole nodes only knows the hostnames of clients it personally handed a DHCP lease to — its DNS resolver has no visibility into what another node's DHCP server is doing. In practice this means a device's hostname can fail to resolve depending on which node happens to answer a given DNS query.

Every push fixes this for VLAN static reservations: it publishes an ip hostname DNS record on every node for each VLAN host that has a hostname set. Only entries whose IP falls inside one of your VLANs' subnets are ever touched — anything else already configured under Pi-hole's own Local DNS Records (custom entries, go-links, etc.) is left completely alone.

Replication

What it's for Open →

Compares Pi-hole settings across every node and, for anything that differs, keeps whichever value changed most recently and pushes it to the rest — using a local change-detection ledger, since Pi-hole's API doesn't expose per-field modification times.

Toggles at the bottom of the page let you choose exactly which settings groups participate (DHCP scope, static reservations, DNS upstreams, local DNS records, conditional forwarding, blocking state, etc.) — anything toggled off is left alone on every node, even if it differs. On by default for most groups; off by default for Blocking state (so you can pause blocking on one node for testing without it silently flipping everywhere) and Groups & client assignments (a bigger, more invasive change — see below).

Groups & client assignments reconciles Pi-hole's group definitions and every client's group membership fleet-wide. This is matched by name (for groups) and by client identifier (for clients) rather than by Pi-hole's internal numeric id — group ids are assigned locally per node, so the same group can end up with a completely different id on each one if created independently. Enabling this will auto-create a missing group on other nodes, which is why it defaults off.

Adlists & domain allow/deny overrides (Blocklists category, both off by default) extend the same name/address-matched reconciliation to gravity.db: adlist URLs (matched by address) and individual exact/regex domain overrides (matched by type+kind+domain). This is what actually keeps "is this domain blocked" consistent fleet-wide — the config.toml settings above never touch gravity.db at all, so without this, a domain whitelisted on one node stays blocked on the others. Enabling either triggers a gravity update on any node it changes, same reasoning as staggered gravity updates.

Auto-replication: set an interval (minutes) to run this on a schedule instead of only on manual click.

A snapshot of every enabled setting is taken automatically right before each run applies anything — see Backup & rollback if a bad merge needs undoing.

Drift check

A separate, read-only button on the Replication page. Unlike a normal replication run (which actively merges and pushes changes), this only reads every node's current state and reports any setting that disagrees between nodes — nothing is changed. Use it to sanity-check that nodes are actually in sync, independent of what the last merge run reported.

Separately, every replication push is read back from the node it was just applied to, to confirm the value actually landed — rather than just trusting the API's success response. If a push "succeeds" by HTTP status but doesn't verify on read-back, that's logged as a distinct failure.

Failover needs PIHOLE_VIP

What it's for Open →

DHCP is broadcast-based — a client's discovery request has no destination IP to filter on — so if your cluster sits behind a keepalived virtual IP (VIP) for DNS, that VIP does nothing to stop every node's embedded DHCP server from independently answering every request. Left alone, all 3 nodes will happily hand out conflicting leases from the same pool at once.

This tab polls (over SSH) for which physical node currently holds the VIP, then uses Pi-hole's API to keep DHCP active only on that node — and re-checks continuously, so a node that gets manually re-enabled (or missed a previous check) is corrected automatically on the next pass.

Requires PIHOLE_VIP to be set in the environment (e.g. 192.168.1.100) — without it, the toggle can still be flipped on but does nothing, and the page shows a warning banner saying so. If your cluster has no VIP at all, just leave this disabled; every other feature in the app works the same either way.

Stats

What it's for Open →

Pi-hole's own dashboard only ever shows one node — this merges query totals (total, blocked, forwarded, cached, % blocked) and top-domain/top-client lists across every reachable node into one view, plus a per-node breakdown.

The top-domains/top-clients lists are summed from each node's own top-10 list, not an exhaustive per-domain count across the whole fleet (Pi-hole's API has no cheap way to compute that) — good for "what's dominating right now," not a precise source of truth for long-tail analysis.

Search query log across the fleet (further down the page) fans a domain and/or client-IP search out to every node's own query log and merges the results, tagged with which node answered — Pi-hole's own dashboard only ever shows one node's log, so this is the fastest way to answer "was this domain blocked, and where."

Updater

What it's for Open →

Checks each node's Pi-hole software version and can upgrade it (pihole -up, then reboots). One node is auto-upgraded per day on a rotating schedule (so the whole fleet is never mid-upgrade at once), and you can trigger any individual node manually at any time. Upgrade history (upgraded / already up to date / failed) is kept per node. A snapshot is taken automatically before every upgrade attempt — see Backup & rollback.

Post-upgrade health gate: a pihole -up that exits clean isn't proof the node actually still works — after the reboot, this runs the same ping→DNS→API health check the monitor itself uses (waiting UPDATER_POST_UPGRADE_WAIT_SECS first). If that check fails, the result is recorded as upgrade_health_failed and the daily round-robin halts — it will not advance to the next node the following day — until you click Resume rotation on this page. A hard upgrade failure (retries exhausted) halts the same way. This is what stops a bad Pi-hole release from silently rolling across the whole fleet, one node per day.

Staggered gravity updates

What it's for Open → (same page as Updater)

A separate rotation from the software updater, on the same Updater page: one node updates its blocklists (pihole -g / gravity) per day, at an hour offset from PIHOLE_UPDATER_HOUR so the two schedules never collide.

A blocklist URL that's briefly unreachable can be silently skipped or served from cache rather than erroring — Pi-hole gives no reliable success signal beyond "the command exited 0." After every update, this compares the node's total blocklist domain count (summed across all enabled block lists) against its own count before the update; a drop larger than GRAVITY_DROP_THRESHOLD_PERCENT (default 10%) is logged as a probable partial-update failure instead of silently accepted as a smaller-but-successful blocklist. A snapshot is taken automatically before every gravity update — see Backup & rollback.

Recovery

What it's for Open →

Pi-hole's own Teleporter backup is config-only — it doesn't contain the real gravity/query databases, so it's a poor way to actually rebuild a node. This tab instead clones a healthy, currently-running node directly onto a target: settings, DHCP static reservations, groups and client group assignments, adlists and domain allow/deny overrides, and every VLAN's dnsmasq.d scope — then triggers a gravity update on the target so its blocklists populate correctly (against the cloned adlists, not whatever the target happened to have before).

This is a deliberate one-way overwrite, not a merge — unlike Replication (which compares nodes and keeps whichever changed most recently), Recovery assumes the target has nothing worth preserving. Use it after reprovisioning a wiped or replaced node, never against a node that's still holding its own live, wanted state.

Stale lease conflicts

What it's for Open → (bottom of VLANs page)

A known Pi-hole footgun: giving a client a static DHCP reservation doesn't retroactively evict a dynamic lease it already holds — the lease database can keep answering with the old IP until it's manually cleared (or FTL restarted). This checks every node's active leases against every static reservation (the primary scope and every VLAN) and flags any MAC whose current active lease doesn't match its reservation.

Each flagged conflict can be cleared directly from the same page — it deletes the stale lease via Pi-hole's API so the client picks up its correct reserved IP on its next renewal.

External DHCP-source sync opt-in, UniFi only

What it's for Open → (bottom of Setup page)

For a different topology than this app otherwise assumes: Pi-hole handling DNS only, with DHCP actually served by a separate platform (UniFi, pfSense, OPNsense). In that setup Pi-hole never sees a DHCP lease, so every client shows up as "Unknown" — this closes that gap by pulling the client name/MAC/IP list from the external platform and publishing it as local DNS records on every node, the same mechanism the VLAN hostname sync uses.

Entirely inert unless EXTERNAL_DHCP_SOURCE is set. Only a UniFi OS (UDM-family) controller is currently implemented, and it has not been exercised against real UniFi hardware — treat it as best-effort until verified. pfSense/OPNsense support doesn't exist yet.

Backup & rollback

What it's for Open →

Multi-master replication faithfully propagates mistakes too — a bad setting changed on one node wins the recency contest and lands on every node, and Recovery can't help because every "healthy peer" now has the same bad config. This tab snapshots every node's replication-managed settings, static reservations, groups, client assignments, adlists, and domain overrides to a file, so there's always something to roll back to.

When snapshots are taken: automatically right before every replication push, gravity update, and software upgrade attempt; on-demand via Back up now; and optionally on a daily/weekly/monthly schedule. Keeps the most recent snapshots (1–5, your choice) — older ones are pruned automatically.

Rolling back restores a chosen snapshot to one specific node or the whole fleet, then triggers a gravity update on whatever it touched. This is a one-way overwrite, same as Recovery — not a merge.

NetBox import opt-in

What it's for Open → (Setup page)

Reads VLANs from NetBox's IPAM and, for each one's associated Prefix, every IP Address in that prefix that's assigned to a device or VM interface with a MAC address — as candidate static host reservations (hostname from the IP's DNS name, falling back to the device/VM name).

Gateway and the DHCP-issuable range aren't modeled in NetBox, so both are a best-effort guess (first usable host as gateway) — review and edit on the VLANs page after import, don't trust them blindly. Entirely read-only against NetBox; requires NETBOX_URL and NETBOX_TOKEN — inert otherwise.

Notifications opt-in

A generic webhook (NOTIFY_WEBHOOK_URL) — no specific provider baked in, so it works with Home Assistant's REST API, ntfy, a Telegram bridge, n8n, or anything else that accepts a webhook. POSTs a small JSON payload (event, message, severity, source) on:

  • A node still down after all SSH reboot retries are exhausted (or skipped for lack of quorum)
  • A gravity update flagged as a probable partial failure, or a hard gravity failure
  • An upgrade failure, or a failed post-upgrade health check

Delivery is fire-and-forget in a background thread, so a slow/unreachable webhook endpoint never blocks the action that triggered it. Inert unless the URL is set.

Fleet nodes

What it's for Open → (top of Setup page)

The list of Pi-hole node IPs every feature in this app operates on. PIHOLE_IPS seeds this list once on first boot; after that, this UI-managed list is authoritative, not the environment variable. Add or remove a node here and every loop (health monitor, replication, updater, gravity, failover) picks up the change immediately — no container recreate needed.

Removing a node here only stops this app from managing/monitoring it — it doesn't touch the node itself. Add a new node here first, then run SSH trust setup and (optionally) Recovery to clone a healthy peer onto it.

Admin login off by default

What it's for Open → (top of Setup page)

By default, every page and API endpoint is open to anyone who can reach this app — fine behind a trusted LAN, not fine if that changes. Flip the switch on the Setup page, set a password once, and every page/API call requires it afterward (session-based — log in once per browser, not per request).

The password is written back into this stack's own .env (ADMIN_PASSWORD), the same write-back technique the SSH key uses, so it survives a container recreate and isn't only sitting in the /data volume. /api/known-hosts stays reachable without a session either way — other apps (e.g. Network-Health) poll it directly for Pi-hole DHCP awareness, and gating it would silently break that integration.

Setup (SSH trust)

What it's for Open →

Everything that writes files to a node (VLAN pushes) needs SSH access. This tab bootstraps that: generates an ed25519 keypair (or reuses an existing one) and distributes the public half to every configured node using a one-time password, so day-to-day operation afterward needs no stored password at all — just the key.

Run this once when first setting the app up, and again (with Regenerate) if you ever need to rotate the key. Per-node status here also doubles as a connectivity/permissions check — it verifies both SSH key auth and passwordless sudo for the configured SSH user.

This same page also has Fleet Nodes (add/remove nodes), NetBox import, and Admin login.

Activity log

What it's for Open →

A unified, filterable history of everything the app has done across every feature — VLAN/host edits, pushes (and any validation that blocked one), replication runs (including health warnings and verification failures), upgrades, and DHCP failovers. This is the first place to check after anything unexpected happens.

Health

What it's for Open →

Independent, always-on monitoring for every physical node: a three-layer check every MONITOR_CHECK_INTERVAL seconds (ping → DNS resolution against MONITOR_DOMAINS → Pi-hole API reachability), a response-time sparkline per node, uptime, current blocking status, and 24h query totals. Adjustable live from a dropdown on the page itself (1–60 min) without touching environment variables.

Down confirmation: a single failed probe never immediately marks a node down — it must fail MONITOR_CONFIRM_ATTEMPTS times in a row (default 3), spaced MONITOR_CONFIRM_INTERVAL_SECS apart (default 45s), before the node is reported/shown as down. This avoids a false alarm from a single transient blip (e.g. a node briefly under heavy load from something like a Diagnostics run causing one slow DNS response). A healthy probe still returns immediately, so this adds no delay to normal checks — only to a node that's actually failing.

Auto-heal: a node that fails MONITOR_REBOOT_AFTER consecutive checks gets an SSH reboot, then up to MONITOR_REBOOT_RETRIES more attempts spaced MONITOR_REBOOT_AFTER_MINUTES apart if it's still down. Every attempt is gated on cluster quorum (at least 2 other nodes healthy) so this never fires while the cluster itself may be the problem. If all retries are exhausted, the node is left down and flagged in the failure log — there's no hypervisor-level escalation, on purpose, so a bad reboot loop can't take out the underlying VM/LXC too.

VIP master & manual failover — tracks which physical node currently holds the keepalived VIP and keeps a history of master changes, plus a one-click manual failover (restarts keepalived on the current master so the backup takes over). Entirely hidden from this page if PIHOLE_VIP isn't set — see Failover above for the DHCP-specific half of VIP handling.

Diagnostics — runs a scripted health dump on a node over SSH (system resources, pihole-FTL/keepalived status and journals, DNS resolution tests, DHCP config/leases, rate-limiting activity) and pulls the report back into fleet-manager's own /data volume, browsable from the "Saved diagnostics" list on this page — it doesn't just sit on the node unreachable. Keeps the most recent MONITOR_MAX_DIAG_REPORTS (default 3) reports per node — running it again on the same node prunes that node's oldest report, other nodes' reports are untouched.

Maintenance mode — put a node into maintenance before working on it by hand (a "Start maintenance" button on each node card, minutes-based, always auto-expires — no permanent-off option). While active, this app's own automation leaves that node alone: no auto-reboot escalation, no DHCP failover enforcement, and it's skipped by replication/drift/gravity/updater auto-rotation (each retries it again next cycle). Health checks themselves keep running for visibility — only the automated reactions are paused.

Requires ping/dig and the NET_RAW capability in the container — both are already set up in the published image and docker-compose.yml.

Troubleshooting & tips
  • A push says "blocked by validation" — two VLANs overlap, or a host/gateway/range falls outside its own VLAN's subnet. Fix the offending VLAN on the VLANs tab; nothing is written to any node until validation passes.
  • A push warns about a missing group — the VLAN's Pi-hole Group name doesn't exist yet on that node. Create it there directly, or enable Groups & client assignments replication so it propagates automatically.
  • Replication says "fewer than 2 Pi-holes reachable" — check the Setup tab for SSH/API connectivity to each node; replication needs at least 2 reachable nodes to have anything to compare.
  • Failover toggle does nothing — PIHOLE_VIP isn't set in the environment. This is expected and safe if your cluster has no VIP.
  • A device's hostname won't resolve from some nodes/VLANs but not others — that's the exact problem fleet-wide hostname resolution exists to fix; make sure the host has a hostname set and a static reservation (dynamic leases aren't published), then push.
  • Something looks stale after an edit — most pages poll automatically every few seconds, but the VLANs page only reflects a push after you actually click the push button; editing a VLAN or host alone doesn't touch the live nodes.
  • Gravity update flagged as "dropped" — the node's blocklist domain count fell by more than GRAVITY_DROP_THRESHOLD_PERCENT after an update. Check that node's own internet/DNS connectivity and whether a specific blocklist URL is down; re-run the update once that's fixed.
  • Recovery clone reports errors partway through — the log shows exactly which step failed (settings, groups/clients, or the VLAN push); the earlier steps that already succeeded are not rolled back, so it's usually safe to just re-run the clone once the underlying issue (e.g. a stale SSH key on the target) is fixed.
  • External DHCP sync shows "Not configured" — expected unless EXTERNAL_DHCP_SOURCE and the matching UniFi credentials are set; this feature is inert by default.
  • Every node on the Health page shows "ping_failed" — the container is missing the ping/dig binaries or the NET_RAW capability. Both are already included in the published image and docker-compose.yml; if you're on a custom build or a bare docker run, make sure iputils-ping/dnsutils are installed and --cap-add=NET_RAW is set.
  • Reboot/Diagnostics silently fails with "Access denied" or "Please run as root" — PIHOLE_SSH_USER is a non-root account without passwordless sudo for reboot/systemctl/the diagnostics script. See Setup and the SSH account requirements above.
  • Updater shows a red "rotation halted" banner — an upgrade either failed outright or failed its post-upgrade health check. Fix the affected node, confirm it's healthy on the Health page, then click Resume rotation on the Updater page.
  • Locked out after enabling Admin login — the password is written to this stack's .env as ADMIN_PASSWORD; set it back to blank there and restart the container to disable login entirely without needing to authenticate first.
  • NetBox scan finds nothing / a VLAN has 0 hosts — the VLAN needs an associated Prefix in NetBox's IPAM, and hosts need an IP Address assigned to a device/VM interface that has a MAC address set (not just an IP with no assignment). Check NETBOX_URL/ NETBOX_TOKEN are set and NETBOX_VERIFY_SSL matches your NetBox's cert.
  • Rollback reports errors partway through — same pattern as Recovery: the log shows exactly which node/step failed, earlier successful steps aren't undone, and it's usually safe to re-run the rollback once the underlying issue (e.g. a node unreachable at rollback time) is fixed.
