Overview

Pihole Fleet Manager is a sidecar app for a multi-node Pi-hole v6 cluster. Pi-hole itself has no concept of "the other nodes" — every Pi-hole instance is independent, so this app is what makes a group of them behave like one fleet: one place to define extra DHCP scopes, one place to keep settings in sync, one place to see what changed and when.

Everything here talks directly to each node's own IP address (set via PIHOLE_IPS) and, for anything that needs to write files, over SSH. Nothing requires a load balancer or virtual IP in front of the cluster — the one exception is the Failover tab, which is entirely optional. See that section below.

VLANs & DHCP scopes

What it's for Open →

Pi-hole's own Settings page only lets you configure one DHCP scope. This tab lets you define any number of additional scopes ("VLANs") — each with its own subnet, gateway, IP range, lease time, and static host reservations — and pushes them out to every node as a dnsmasq.d config snippet, alongside Pi-hole's native scope.

The "Primary" VLAN at the top of the list isn't something you create — it's a read-only mirror of whatever DHCP scope is already configured natively in Pi-hole's own Settings. Its hosts are the actual reservations from Pi-hole's API, always live, not stored locally.

Adding hosts: expand a VLAN and use the form at the bottom to reserve a MAC → IP (with an optional hostname). Any device that already has an active lease in that VLAN's subnet shows up automatically, tagged DYNAMIC — click its IP or MAC to turn it into a permanent static reservation.

Conditional Forward Domain (optional, per VLAN): Pi-hole's own Settings UI only supports one conditional-forwarding domain/subnet fleet-wide. Setting this per VLAN lets devices in that VLAN resolve local domain names (e.g. reverse DNS for a router's own admin hostname) without touching Pi-hole's native single setting.

Pi-hole Group (optional, per VLAN): see Group assignment below.

Push to Pi-hole

Nothing you do on the VLANs tab takes effect on the actual Pi-hole nodes until you click Push scopes to all Pi-holes. A push does all of the following, per node, in order:

  • Validates the full VLAN set first — if any two VLANs overlap, or a host/range falls outside its own subnet, the entire push is blocked before anything is written anywhere.
  • Writes the rendered dnsmasq.d file over SSH.
  • Flips Pi-hole's misc.etc_dnsmasq_d setting on so the file actually gets read.
  • Reloads DNS (pihole restartdns) so the new scopes take effect immediately.
  • Syncs VLAN-derived hostname DNS records — see Hostname resolution.
  • Assigns each VLAN's clients to its configured Pi-hole group, if one is set — see Group assignment.

Use Preview generated config to see exactly what will be written, without pushing anything. If a node already has scopes from a different/older instance pointed at the same cluster, the Import flow (on the same page) can pull those back into the local store instead of you re-entering them by hand.

Per-VLAN group assignment

Pi-hole supports assigning different blocklist policies ("groups") to different clients — but only per individual client (by MAC/IP), never per subnet/VLAN. Setting a Pi-hole Group name on a VLAN (on the VLANs tab) closes that gap: every push assigns every client currently in that VLAN — static reservations and active dynamic leases alike — to the named group, via Pi-hole's /api/clients.

The group itself has to already exist on a node for this to take effect there — if it doesn't yet, the push logs a warning for that node (rather than failing the whole push) telling you the group name wasn't found. Create the group once on any node's own Pi-hole UI (Group Management), or let replication's group reconciliation propagate it to the rest of the fleet automatically.

Fleet-wide hostname resolution

Each of the 3 Pi-hole nodes only knows the hostnames of clients it personally handed a DHCP lease to — its DNS resolver has no visibility into what another node's DHCP server is doing. In practice this means a device's hostname can fail to resolve depending on which node happens to answer a given DNS query.

Every push fixes this for VLAN static reservations: it publishes an ip hostname DNS record on every node for each VLAN host that has a hostname set. Only entries whose IP falls inside one of your VLANs' subnets are ever touched — anything else already configured under Pi-hole's own Local DNS Records (custom entries, go-links, etc.) is left completely alone.

Replication

What it's for Open →

Compares Pi-hole settings across every node and, for anything that differs, keeps whichever value changed most recently and pushes it to the rest — using a local change-detection ledger, since Pi-hole's API doesn't expose per-field modification times.

Toggles at the bottom of the page let you choose exactly which settings groups participate (DHCP scope, static reservations, DNS upstreams, local DNS records, conditional forwarding, blocking state, etc.) — anything toggled off is left alone on every node, even if it differs. On by default for most groups; off by default for Blocking state (so you can pause blocking on one node for testing without it silently flipping everywhere) and Groups & client assignments (a bigger, more invasive change — see below).

Groups & client assignments reconciles Pi-hole's group definitions and every client's group membership fleet-wide. This is matched by name (for groups) and by client identifier (for clients) rather than by Pi-hole's internal numeric id — group ids are assigned locally per node, so the same group can end up with a completely different id on each one if created independently. Enabling this will auto-create a missing group on other nodes, which is why it defaults off.

Auto-replication: set an interval (minutes) to run this on a schedule instead of only on manual click.

Drift check

A separate, read-only button on the Replication page. Unlike a normal replication run (which actively merges and pushes changes), this only reads every node's current state and reports any setting that disagrees between nodes — nothing is changed. Use it to sanity-check that nodes are actually in sync, independent of what the last merge run reported.

Separately, every replication push is read back from the node it was just applied to, to confirm the value actually landed — rather than just trusting the API's success response. If a push "succeeds" by HTTP status but doesn't verify on read-back, that's logged as a distinct failure.

Failover needs PIHOLE_VIP

What it's for Open →

DHCP is broadcast-based — a client's discovery request has no destination IP to filter on — so if your cluster sits behind a keepalived virtual IP (VIP) for DNS, that VIP does nothing to stop every node's embedded DHCP server from independently answering every request. Left alone, all 3 nodes will happily hand out conflicting leases from the same pool at once.

This tab polls (over SSH) for which physical node currently holds the VIP, then uses Pi-hole's API to keep DHCP active only on that node — and re-checks continuously, so a node that gets manually re-enabled (or missed a previous check) is corrected automatically on the next pass.

Requires PIHOLE_VIP to be set in the environment (e.g. 192.168.1.100) — without it, the toggle can still be flipped on but does nothing, and the page shows a warning banner saying so. If your cluster has no VIP at all, just leave this disabled; every other feature in the app works the same either way.

Stats

What it's for Open →

Pi-hole's own dashboard only ever shows one node — this merges query totals (total, blocked, forwarded, cached, % blocked) and top-domain/top-client lists across every reachable node into one view, plus a per-node breakdown.

The top-domains/top-clients lists are summed from each node's own top-10 list, not an exhaustive per-domain count across the whole fleet (Pi-hole's API has no cheap way to compute that) — good for "what's dominating right now," not a precise source of truth for long-tail analysis.

Updater

What it's for Open →

Checks each node's Pi-hole software version and can upgrade it (pihole -up, then reboots). One node is auto-upgraded per day on a rotating schedule (so the whole fleet is never mid-upgrade at once), and you can trigger any individual node manually at any time. Upgrade history (upgraded / already up to date / failed) is kept per node.

Staggered gravity updates

What it's for Open → (same page as Updater)

A separate rotation from the software updater, on the same Updater page: one node updates its blocklists (pihole -g / gravity) per day, at an hour offset from PIHOLE_UPDATER_HOUR so the two schedules never collide.

A blocklist URL that's briefly unreachable can be silently skipped or served from cache rather than erroring — Pi-hole gives no reliable success signal beyond "the command exited 0." After every update, this compares the node's total blocklist domain count (summed across all enabled block lists) against its own count before the update; a drop larger than GRAVITY_DROP_THRESHOLD_PERCENT (default 10%) is logged as a probable partial-update failure instead of silently accepted as a smaller-but-successful blocklist.

Recovery

What it's for Open →

Pi-hole's own Teleporter backup is config-only — it doesn't contain the real gravity/query databases, so it's a poor way to actually rebuild a node. This tab instead clones a healthy, currently-running node directly onto a target: settings, DHCP static reservations, groups and client group assignments, and every VLAN's dnsmasq.d scope — then triggers a gravity update on the target so its blocklists populate too.

This is a deliberate one-way overwrite, not a merge — unlike Replication (which compares nodes and keeps whichever changed most recently), Recovery assumes the target has nothing worth preserving. Use it after reprovisioning a wiped or replaced node, never against a node that's still holding its own live, wanted state.

Stale lease conflicts

What it's for Open → (bottom of VLANs page)

A known Pi-hole footgun: giving a client a static DHCP reservation doesn't retroactively evict a dynamic lease it already holds — the lease database can keep answering with the old IP until it's manually cleared (or FTL restarted). This checks every node's active leases against every static reservation (the primary scope and every VLAN) and flags any MAC whose current active lease doesn't match its reservation.

Each flagged conflict can be cleared directly from the same page — it deletes the stale lease via Pi-hole's API so the client picks up its correct reserved IP on its next renewal.

External DHCP-source sync opt-in, UniFi only

What it's for Open → (bottom of Setup page)

For a different topology than this app otherwise assumes: Pi-hole handling DNS only, with DHCP actually served by a separate platform (UniFi, pfSense, OPNsense). In that setup Pi-hole never sees a DHCP lease, so every client shows up as "Unknown" — this closes that gap by pulling the client name/MAC/IP list from the external platform and publishing it as local DNS records on every node, the same mechanism the VLAN hostname sync uses.

Entirely inert unless EXTERNAL_DHCP_SOURCE is set. Only a UniFi OS (UDM-family) controller is currently implemented, and it has not been exercised against real UniFi hardware — treat it as best-effort until verified. pfSense/OPNsense support doesn't exist yet.

Setup (SSH trust)

What it's for Open →

Everything that writes files to a node (VLAN pushes) needs SSH access. This tab bootstraps that: generates an ed25519 keypair (or reuses an existing one) and distributes the public half to every configured node using a one-time password, so day-to-day operation afterward needs no stored password at all — just the key.

Run this once when first setting the app up, and again (with Regenerate) if you ever need to rotate the key. Per-node status here also doubles as a connectivity/permissions check — it verifies both SSH key auth and passwordless sudo for the configured SSH user.

Activity log

What it's for Open →

A unified, filterable history of everything the app has done across every feature — VLAN/host edits, pushes (and any validation that blocked one), replication runs (including health warnings and verification failures), upgrades, and DHCP failovers. This is the first place to check after anything unexpected happens.

Troubleshooting & tips
  • A push says "blocked by validation" — two VLANs overlap, or a host/gateway/range falls outside its own VLAN's subnet. Fix the offending VLAN on the VLANs tab; nothing is written to any node until validation passes.
  • A push warns about a missing group — the VLAN's Pi-hole Group name doesn't exist yet on that node. Create it there directly, or enable Groups & client assignments replication so it propagates automatically.
  • Replication says "fewer than 2 Pi-holes reachable" — check the Setup tab for SSH/API connectivity to each node; replication needs at least 2 reachable nodes to have anything to compare.
  • Failover toggle does nothing — PIHOLE_VIP isn't set in the environment. This is expected and safe if your cluster has no VIP.
  • A device's hostname won't resolve from some nodes/VLANs but not others — that's the exact problem fleet-wide hostname resolution exists to fix; make sure the host has a hostname set and a static reservation (dynamic leases aren't published), then push.
  • Something looks stale after an edit — most pages poll automatically every few seconds, but the VLANs page only reflects a push after you actually click the push button; editing a VLAN or host alone doesn't touch the live nodes.
  • Gravity update flagged as "dropped" — the node's blocklist domain count fell by more than GRAVITY_DROP_THRESHOLD_PERCENT after an update. Check that node's own internet/DNS connectivity and whether a specific blocklist URL is down; re-run the update once that's fixed.
  • Recovery clone reports errors partway through — the log shows exactly which step failed (settings, groups/clients, or the VLAN push); the earlier steps that already succeeded are not rolled back, so it's usually safe to just re-run the clone once the underlying issue (e.g. a stale SSH key on the target) is fixed.
  • External DHCP sync shows "Not configured" — expected unless EXTERNAL_DHCP_SOURCE and the matching UniFi credentials are set; this feature is inert by default.
